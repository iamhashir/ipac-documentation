## OQ-002 {#oq-002}

### What هو ال live role set, و هو there a hierarchy? {#what-is-the-live-role-set-and-is-there-a-hierarchy}

**Impact: High. الحالة: closed 2026-08-20.**

**What تم observed.** المصدر references six role names: `admin`, `director`,
`executive`, `sales`, `client`, `packer`. Four enforcement points use **مختلف
subsets**, documented في full at
[Roles و permissions](/docs/website/roles-and-permissions). Two internal
documents — `website/docs/ROLES.md` و `website/AGENTS.md` — assert that ال live
`roles.name` rows هي `admin, client, executive, packer, sales`, و that
`director`, `project_lead`, `team_lead` و `customer` هي code-only. `AGENTS.md`
explicitly warns against reconciling ال layers without verifying all من them.

**Resolved من live Supabase.** `roles.name` rows هي `admin`, `client`,
`executive`, `packer`, و `sales`. They هي مستخدم بواسطة 35 profiles: 4 admin,
4 client, 1 executive, 25 packer, و 1 sales.

**Why it matters.** إذا `director` does لا exist live, then مستخدم creation via ال
Edge Function works لـ `admin` only, و attendance management reduces إلى `admin`
plus per-order team leads — مع nothing failing loudly. Meanwhile `executive`,
which ال documents call live, هو locked out من Mobile entirely.

**Residual.** There هو no live hierarchy object. Any hierarchy remains a product
أو code convention, لا a قاعدة البيانات primitive.

## OQ-004 {#oq-004}

### هو ال `.docs/` reference set و worklog protocol still في force? {#is-the-docs-reference-set-and-worklog-protocol-still-in-force}

**Impact: Medium. الحالة: مفتوح.**

**What تم observed.** `website/CLAUDE.md` instructs contributors إلى consult
reference documents في a `.docs/` directory — data flow, قاعدة البيانات schema, query
patterns, component الهندسة, input validation و CI/CD setup — و describes
a **mandatory** worklog protocol requiring every completed task إلى be appended إلى
`.docs/engineering-worklog.md`.

**No `.docs/` directory exists.** Re-confirmed on 2026-08-19 against ال canonical
`ipacapps/website` checkout, لا only ال older one. None من ال seven ملفات هي
present.

**Why it matters.** A new contributor following `CLAUDE.md` looks لـ guidance that
هو لا there, و cannot satisfy a protocol described as mandatory. It هو also
unclear whether those documents once existed و تم lost, أو تم never written.

**Why this هو a decision, لا a lookup.** ال fact هو تم التحقق. What remains هو
choosing whether ال worklog protocol هو still required, و whether those
reference documents ينبغي be restored في `website` أو replaced بواسطة pages on this
site. Until then, do لا treat ال worklog protocol as an active requirement.

Note that `website/AGENTS.md` **does** contain real, الحالي governance — a
قاعدة البيانات Safety policy و a six-step قاعدة البيانات Change Process. That هو ال material
worth adopting; see
[الأمان model](/docs/security/model) و
[Schema provenance](/docs/backend/schema-provenance#restoring-reproducibility).

## OQ-011 {#oq-011}

### Where ينبغي قاعدة البيانات migrations live, و how do we baseline? {#where-should-database-migrations-live-and-how-do-we-baseline}

**Impact: High. الحالة: مفتوح — live values resolved, transitions pending.**

**What تم observed.** `website` has **no `supabase/` directory**. ال only
migration في either المستودع هو one ملف في `Mobile`. A migration named
`prefer_instance_packed_at_in_reports` تم applied إلى ال live project و later
reverted, و exists في **no** المستودع. A second, `add_packing_start_completion_date_modes`,
exists only as an uncommitted ملف في an older محلي checkout.

**Why it matters.** 67 live tables و 83 live functions have one migration
between them.
There هو no reviewable history, no revert مسار, و no way إلى create an
البيئة that provably matches الإنتاج.

**What would resolve it.** A decision on where migrations live, followed بواسطة a
baseline dump من ال الحالي schema as a first migration. See
[Schema provenance](/docs/backend/schema-provenance#restoring-reproducibility).

## OQ-012 {#oq-012}

does لا recognise passes silently.

**What would resolve it.** A product decision on ال legal transitions. Consider
a check constraint أو enum afterwards.

## OQ-013 {#oq-013}

### What هي ال 24 uncalled قاعدة البيانات functions لـ? {#what-are-the-24-uncalled-database-functions-for}

**Impact: Medium. الحالة: مفتوح.**

**What تم observed.** 24 من 49 declared functions هي called بواسطة neither
التطبيق, listed في [قاعدة البيانات model](/docs/backend/database-model#functions).
Two قراءة like scheduled أو trigger work — `deactivate_expired_privileges` و
`refresh_order_pkg_overview_rollup` — و `deactivate_expired_privileges` هو ال
only mechanism that would make `temporary_privileges` function.

**Why it هو unresolved.** No المستودع يحتوي a trigger definition أو a
scheduled-job الإعداد. Any classification would be inference.

**Why it matters.** إذا these هي trigger bodies, they change state as a side
effect من يكتب that التطبيق code appears إلى control. إذا they هي dead code,
they هي noise that obscures ال real surface.

**What would resolve it.** Dump `pg_trigger` و any scheduled jobs, then
cross-reference.

## OQ-014 {#oq-014}

### What هي ال live RLS policies on `packer_sessions`? {#what-are-the-live-rls-policies-on-packersessions}

**Impact: High. الحالة: closed 2026-08-20.**

**What تم observed.** ال one migration في ال المستودعات creates a
`packer_sessions` manage policy predicated on `orders.status IN ('pending','in_progress')`.
**`orders` has no `status` column** في ال schema snapshot, و no التطبيق code
يقرأ one. ال migration `DROP POLICY IF EXISTS`es three policies قبل creating
ال new ones.

**Resolved من live Supabase.** ال live manage policy يستخدم
`orders.production_status IN ('pending','in_progress')`, لا ال المفقود
`orders.status` column. ال table has three live policies. One هو a temporary
broad authenticated policy; that هو now a الأمان review item, لا an unanswered
catalog سؤال.

## OQ-016 {#oq-016}

### هي ال `roles` permission flags enforced anywhere? {#are-the-roles-permission-flags-enforced-anywhere}

**Impact: Medium. الحالة: مفتوح.**

**What تم observed.** `roles` carries six booleans (`can_manage_roles`,
`can_ban_users`, `can_block_users`, `can_delete_profiles`, `can_reset_passwords`,
`can_unblock_users`). A `user_effective_permissions` view exists, as do
`user_has_permission` و `get_user_role`. **No التفويض مسار في either
التطبيق أو ال Edge Function يقرأ any من them** — `create-user` even selects
`can_manage_roles` و then ignores it.

**Resolved من live Supabase.** ال flags هي enforced في قاعدة البيانات helpers و
RLS. `roles` policies call `user_has_permission('can_manage_roles')`, و
`profiles` policies call `user_has_permission('can_block_users')` لـ a
`project_lead` مسار. ال live `user_effective_permissions` view also merges base
role flags مع active temporary privileges.

## OQ-019 {#oq-019}

### هو `audit_log` a complete record من مستخدم creation? {#is-auditlog-a-complete-record-of-user-creation}

**Impact: Medium. الحالة: مفتوح.**

**What تم observed.** ال `create-user` Edge Function يكتب an `audit_log` row
لـ every account it creates. An incident log records at least one account أنشئ
بواسطة **مباشر SQL insert** into `auth.users`, bypassing ال function — و therefore
its audit كتابة و its role check.

**Why it matters.** إذا `audit_log` هو incomplete, it cannot be مستخدم إلى answer "who
أنشئ this account" during an incident أو review.

**What would resolve it.** Compare `auth.users` against `audit_log` entries مع
`entity_type = 'profile'` و `action_type = 'INSERT'`.

### How هو "one active order per packer" enforced? {#how-is-one-active-order-per-packer-enforced}

**What تم observed.** `profiles.current_order_id` exists.

## OQ-023 {#oq-023}

### What keeps `packer_sessions` denormalised fields fresh? {#what-keeps-packersessions-denormalised-fields-fresh}

**Impact: Low. الحالة: مفتوح.**

**What تم observed.** `packer_sessions` stores `order_name`, `client_name` و

ال session copies هي stale, و any UI reading them shows outdated values.

**What would resolve it.** Check لـ triggers on `orders`, `profiles` و
`packer_sessions`.

## OQ-024 {#oq-024}

### Which تقرير packed-date logic هو live today? {#which-report-packed-date-logic-is-live-today}

**Impact: High. الحالة: closed 2026-08-20.**

**What تم observed.** An incident log records ال تقرير date logic being changed
إلى `COALESCE(order_pkg_instance.packed_at, MAX(pkd_item.created_at))` via a
migration named `prefer_instance_packed_at_in_reports`, و then **reverted on
2026-08-08** إلى `MAX(pkd_item.created_at)`. A further migration named
`add_packing_start_completion_date_modes` exists as an uncommitted ملف في an older
checkout, implying more work followed.

**Resolved من live Supabase.** ال الحالي overload مع `p_tag_ids` يستخدم
`COALESCE(order_pkg_instance.packed_at, MAX(pkd_item.created_at))` لـ
completion-style modes. It accepts `packing_started_at`,
`packing_completed_at`, `item_packed_at`, و falls back إلى instance creation لـ
unrecognised modes. `item_packed_at` هو a legacy alias لـ completion.

## Adding an entry {#adding-an-entry}

Found something ال documentation cannot settle? Add it here rather than guessing,
و mark ال affected page مع an مفتوح سؤال الحالة banner. An entry needs five
things: what تم observed, why it هو unresolved, why it matters, what would resolve
it, و a stable ID so pages يمكن link إلى it. عندما an entry هو answered, move it إلى
ال closed register مع ال date و ال الدليل — do لا delete it.

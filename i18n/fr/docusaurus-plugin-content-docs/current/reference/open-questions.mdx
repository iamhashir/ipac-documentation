## OQ-002 {#oq-002}

### What est le live rôle set, et est there a hierarchy? {#what-is-the-live-role-set-and-is-there-a-hierarchy}

**Impact: High. Statut: closed 2026-08-20.**

**What a été observed.** Source references six rôle names: `admin`, `director`,
`executive`, `sales`, `client`, `packer`. Four enforcement points use **différent
subsets**. Two internal
documents — `website/docs/ROLES.md` et `website/AGENTS.md` — assert that le live
`roles.name` rows sont `admin, client, executive, packer, sales`, et that
`director`, `project_lead`, `team_lead` et `customer` sont code-only. `AGENTS.md`
explicitly warns against reconciling le layers without verifying all de them.

**Resolved depuis live Supabase.** `roles.name` rows sont `admin`, `client`,
`executive`, `packer`, et `sales`. They sont utilisé par 35 profiles: 4 admin,
4 client, 1 executive, 25 packer, et 1 sales.

**Why it matters.** Si `director` does ne exist live, then utilisateur creation via le
Edge Function works pour `admin` only, et attendance management reduces vers `admin`
plus per-order team leads — avec nothing failing loudly. Meanwhile `executive`,
which le documents call live, est locked out de Mobile entirely.

**Residual.** There est non live hierarchy object. Any hierarchy remains a product
ou code convention, ne a base de données primitive.

## OQ-004 {#oq-004}

### est le `.docs/` reference set et worklog protocol still dans force? {#is-the-docs-reference-set-and-worklog-protocol-still-in-force}

**Impact: Medium. Statut: ouverte.**

**What a été observed.** `website/CLAUDE.md` instructs contributors vers consult
reference documents dans a `.docs/` directory — data flow, base de données schema, query
patterns, component architecture, input validation et CI/CD setup — et describes
a **mandatory** worklog protocol requiring every completed task vers be appended vers
`.docs/engineering-worklog.md`.

**Non `.docs/` directory exists.** Re-confirmed on 2026-08-19 against le canonical
`ipacapps/website` checkout, ne only le older one. None de le seven fichiers sont
present.

**Why it matters.** A new contributor following `CLAUDE.md` looks pour guidance that
est ne there, et cannot satisfy a protocol described as mandatory. It est also
unclear whether those documents once existed et ont été lost, ou ont été never written.

**Why this est a decision, ne a lookup.** le fact est vérifié. What remains est
choosing whether le worklog protocol est still required, et whether those
reference documents devrait be restored dans `website` ou replaced par pages on this
site. Until then, do ne treat le worklog protocol as an active requirement.

Note that `website/AGENTS.md` **does** contain real, actuel governance — a
Base de données Safety policy et a six-step Base de données Change Process. That est le material
worth adopting; see
[Sécurité model](/docs/security/model) et
[Schema provenance](/docs/backend/schema-provenance#restoring-reproducibility).

## OQ-016 {#oq-016}

### sont le `roles` permission flags enforced anywhere? {#are-the-roles-permission-flags-enforced-anywhere}

**Impact: Medium. Statut: ouverte.**

**What a été observed.** `roles` carries six booleans (`can_manage_roles`,
`can_ban_users`, `can_block_users`, `can_delete_profiles`, `can_reset_passwords`,
`can_unblock_users`). A `user_effective_permissions` view exists, as do
`user_has_permission` et `get_user_role`. **Non autorisation chemin dans either
application ou le Edge Function lit any de them** — `create-user` even selects
`can_manage_roles` et then ignores it.

**Resolved depuis live Supabase.** le flags sont enforced dans base de données helpers et
RLS. `roles` policies call `user_has_permission('can_manage_roles')`, et
`profiles` policies call `user_has_permission('can_block_users')` pour a
`project_lead` chemin. le live `user_effective_permissions` view also merges base
rôle flags avec active temporary privileges.

## OQ-024 {#oq-024}

### Which rapport packed-date logic est live today? {#which-report-packed-date-logic-is-live-today}

**Impact: High. Statut: closed 2026-08-20.**

**What a été observed.** An incident log records le rapport date logic being changed
vers `COALESCE(order_pkg_instance.packed_at, MAX(pkd_item.created_at))` via a
migration named `prefer_instance_packed_at_in_reports`, et then **reverted on
2026-08-08** vers `MAX(pkd_item.created_at)`. A further migration named
`add_packing_start_completion_date_modes` exists as an uncommitted fichier dans an older

**Resolved depuis live Supabase.** le actuel overload avec `p_tag_ids` utilise
`COALESCE(order_pkg_instance.packed_at, MAX(pkd_item.created_at))` pour
completion-style modes. It accepts `packing_started_at`,
`packing_completed_at`, `item_packed_at`, et falls back vers instance creation pour
unrecognised modes. `item_packed_at` est a legacy alias pour completion.

## OQ-002 {#oq-002}

### What is the live role set, and is there a hierarchy?

**Impact: High. Status: closed 2026-08-20.**

**What was observed.** Source references six role names: `admin`, `director`,
`executive`, `sales`, `client`, `packer`. Four enforcement points use **different
subsets**. Two internal
documents — `website/docs/ROLES.md` and `website/AGENTS.md` — assert that the live
`roles.name` rows are `admin, client, executive, packer, sales`, and that
`director`, `project_lead`, `team_lead` and `customer` are code-only. `AGENTS.md`
explicitly warns against reconciling the layers without verifying all of them.

**Resolved from live Supabase.** `roles.name` rows are `admin`, `client`,
`executive`, `packer`, and `sales`. They are used by 35 profiles: 4 admin,
4 client, 1 executive, 25 packer, and 1 sales.

**Why it matters.** If `director` does not exist live, then user creation via the
Edge Function works for `admin` only, and attendance management reduces to `admin`
plus per-order team leads — with nothing failing loudly. Meanwhile `executive`,
which the documents call live, is locked out of Mobile entirely.

**Residual.** There is no live hierarchy object. Any hierarchy remains a product
or code convention, not a database primitive.

## OQ-004 {#oq-004}

### Is the `.docs/` reference set and worklog protocol still in force?

**Impact: Medium. Status: open.**

**What was observed.** `website/CLAUDE.md` instructs contributors to consult
reference documents in a `.docs/` directory — data flow, database schema, query
patterns, component architecture, input validation and CI/CD setup — and describes
a **mandatory** worklog protocol requiring every completed task to be appended to
`.docs/engineering-worklog.md`.

**No `.docs/` directory exists.** Re-confirmed on 2026-08-19 against the canonical
`ipacapps/website` checkout, not only the older one. None of the seven files are
present.

**Why it matters.** A new contributor following `CLAUDE.md` looks for guidance that
is not there, and cannot satisfy a protocol described as mandatory. It is also
unclear whether those documents once existed and were lost, or were never written.

**Why this is a decision, not a lookup.** The fact is verified. What remains is
choosing whether the worklog protocol is still required, and whether those
reference documents should be restored in `website` or replaced by pages on this
site. Until then, do not treat the worklog protocol as an active requirement.

Note that `website/AGENTS.md` **does** contain real, current governance — a
Database Safety policy and a six-step Database Change Process. That is the material
worth adopting; see
[Security model](/docs/security/model) and
[Schema provenance](/docs/backend/schema-provenance#restoring-reproducibility).

## OQ-006 {#oq-006}

### Which Node version is officially supported?

**Impact: Medium. Status: open — facts resolved, decision pending.**

**Resolved from source.** The active values are:

| Source | Version |
| --- | --- |
| `Mobile/.nvmrc` | 22.19.0 |
| `ipac-documentation/.nvmrc` | 22.19.0 |
| Vercel `ipac-documentation` project | 22.x |
| `website/.github/workflows/pr-validation.yml` | 22.x |
| `website/.github/workflows/ci-cd.yml` | **24.x** |

`website` therefore validates pull requests on one major and builds production on
another — a change can pass review and fail in production. The documentation
repository and Vercel `ipac-documentation` project are aligned on Node 22.x as of
2026-08-20.

**What remains.** Choosing one version for `website`. That is a decision, not a
lookup. This documentation site pins 22.19.0, matching `Mobile`.

## OQ-008 {#oq-008}

### What is the current live schema shape?

**Impact: High. Status: closed 2026-08-20.**

**Resolved from live Supabase.** The live project has 67 public tables, 3 views,
83 public functions, 11 public enums and 17 non-internal triggers. Every live
public table has RLS enabled. The shared-table RLS matrix, storage buckets,
triggers and high-signal grants are documented in
[Live backend verification](/docs/backend/live-verification).

**Residual.** Fresh generated TypeScript types still need to be produced and
compared in a temporary location before deciding whether to overwrite application
types.

## OQ-009 {#oq-009}

### Who may access this documentation site, and on what domain?

**Impact: Medium. Status: open.**

The site is configured to be compatible with Vercel Deployment Protection —
crawling disallowed in `static/robots.txt`, sitemap generation off. Live Vercel
inspection on 2026-08-20 confirmed SSO protection for all deployments except
custom domains, zero aliases, zero team domains, and no environment variables.

**Not decided:** which people or identity provider groups should be allowed, and
whether the placeholder `url` in `docusaurus.config.ts` should remain
`https://ipac-documentation.vercel.app` when no public alias is permitted.

**What would resolve it.** Choose the access audience and final absolute URL
strategy, then update `url` if needed.

## OQ-011 {#oq-011}

### Where should database migrations live, and how do we baseline?

**Impact: High. Status: open — live values resolved, transitions pending.**

**What was observed.** `website` has **no `supabase/` directory**. The only
migration in either repository is one file in `Mobile`. A migration named
`prefer_instance_packed_at_in_reports` was applied to the live project and later
reverted, and exists in **no** repository. A second, `add_packing_start_completion_date_modes`,
exists only as an uncommitted file in an older local checkout.

**Why it matters.** 67 live tables and 83 live functions have one migration
between them.
There is no reviewable history, no revert path, and no way to create an
environment that provably matches production.

**What would resolve it.** A decision on where migrations live, followed by a
baseline dump of the current schema as a first migration. See
[Schema provenance](/docs/backend/schema-provenance#restoring-reproducibility).

## OQ-012 {#oq-012}

### What are the legal order status values and transitions?

**Impact: High. Status: open.**

**What was observed.** `orders` has `production_status` and `commercial_status`,
both **plain strings with no enum and no check constraint** — the database does not
constrain them. Live values on 2026-08-20 are `completed`, `in_progress`,
`on_hold`, `pending` for `production_status`, and `approved`, `draft`,
`invoiced` for `commercial_status`.

**Why it is unresolved.** The live vocabulary is known, but legal transitions are
asserted by no source.

**Why it matters.** Two applications write these columns. A value one application
does not recognise passes silently.

**What would resolve it.** A product decision on the legal transitions. Consider
a check constraint or enum afterwards.

## OQ-013 {#oq-013}

### What are the 24 uncalled database functions for?

**Impact: Medium. Status: open.**

**What was observed.** 24 of 49 declared functions are called by neither
application, listed in [Database model](/docs/backend/database-model#functions).
Two read like scheduled or trigger work — `deactivate_expired_privileges` and
`refresh_order_pkg_overview_rollup` — and `deactivate_expired_privileges` is the
only mechanism that would make `temporary_privileges` function.

**Why it is unresolved.** No repository contains a trigger definition or a
scheduled-job configuration. Any classification would be inference.

**Why it matters.** If these are trigger bodies, they change state as a side
effect of writes that application code appears to control. If they are dead code,
they are noise that obscures the real surface.

**What would resolve it.** Dump `pg_trigger` and any scheduled jobs, then
cross-reference.

## OQ-014 {#oq-014}

### What are the live RLS policies on `packer_sessions`?

**Impact: High. Status: closed 2026-08-20.**

**What was observed.** The one migration in the repositories creates a
`packer_sessions` manage policy predicated on `orders.status IN ('pending','in_progress')`.
**`orders` has no `status` column** in the schema snapshot, and no application code
reads one. The migration `DROP POLICY IF EXISTS`es three policies before creating
the new ones.

**Resolved from live Supabase.** The live manage policy uses
`orders.production_status IN ('pending','in_progress')`, not the missing
`orders.status` column. The table has three live policies. One is a temporary
broad authenticated policy; that is now a security review item, not an unanswered
catalog question.

## OQ-015 {#oq-015}

### Does bucket `order_media` exist, and is it public?

**Impact: High. Status: closed 2026-08-20.**

**What was observed.** `Mobile` uploads package photographs to bucket
**`order_media`** and immediately calls `getPublicUrl()`. `website` reads and
writes bucket **`media`** in six places. Only `media` appears in the schema
snapshot. Filenames are `orderPackageId/timestamp.ext`.

**Resolved from live Supabase.** `order_media` does not exist as a storage bucket
or public table. Live storage buckets are `media` and `signatures`, and both are
public. The Mobile code is therefore misaligned with the live storage model.

## OQ-016 {#oq-016}

### Are the `roles` permission flags enforced anywhere?

**Impact: Medium. Status: open.**

**What was observed.** `roles` carries six booleans (`can_manage_roles`,
`can_ban_users`, `can_block_users`, `can_delete_profiles`, `can_reset_passwords`,
`can_unblock_users`). A `user_effective_permissions` view exists, as do
`user_has_permission` and `get_user_role`. **No authorization path in either
application or the Edge Function reads any of them** — `create-user` even selects
`can_manage_roles` and then ignores it.

**Resolved from live Supabase.** The flags are enforced in database helpers and
RLS. `roles` policies call `user_has_permission('can_manage_roles')`, and
`profiles` policies call `user_has_permission('can_block_users')` for a
`project_lead` path. The live `user_effective_permissions` view also merges base
role flags with active temporary privileges.

### Is phone/SMS authentication enabled in the project?

**Impact: Medium. Status: closed 2026-08-20.**

**What was observed.** `Mobile` implements `signInWithPhone` and `verifyOtp` and
exposes both through `AuthContext`. **No screen calls them.**

**Why it matters.** If phone auth is enabled in the Supabase project, it is an
unmonitored second entry point with no UI and therefore no logging or rate-limit

**What would resolve it.** Check the project's auth provider configuration. If
disabled, delete the code; if enabled, document and monitor it.

## OQ-018 {#oq-018}

### What is the actual Mobile release and distribution process?

**Impact: Medium. Status: open.**

**What was observed.** Three EAS profiles, all producing **Android APKs**;
`appVersionSource: "remote"`; `submit.production` an empty object; **no CI
workflow in `Mobile` at all**; no release script or runbook. `development` and
`preview` declare `distribution: internal`; `production` declares no distribution.

**Why it is unresolved.** Nothing in source states who triggers a build, how the
APK reaches a device, or whether any store is involved. APK-only means Google Play
submission is not possible as configured.

**What would resolve it.** A description from whoever performs releases. See
[Build and release](/docs/mobile/build-and-release#release-process).

## OQ-019 {#oq-019}

### Is `audit_log` a complete record of user creation?

**Impact: Medium. Status: open.**

**What was observed.** The `create-user` Edge Function writes an `audit_log` row
for every account it creates. An incident log records at least one account created
by **direct SQL insert** into `auth.users`, bypassing the function — and therefore
its audit write and its role check.

**Why it matters.** If `audit_log` is incomplete, it cannot be used to answer "who
created this account" during an incident or review.

**What would resolve it.** Compare `auth.users` against `audit_log` entries with
`entity_type = 'profile'` and `action_type = 'INSERT'`.

## OQ-020 {#oq-020}

### How is "one active order per packer" enforced?

**Impact: Medium. Status: open.**

**What was observed.** `profiles.current_order_id` exists.
`update_project_lead_with_status` couples a lead change with a status change.
`website` provides `admin_force_release_packer`, which only makes sense if a packer
can become stuck attached to an order.

**Resolved from live Supabase.** `order_team_members` has an enabled trigger
`trigger_enforce_single_active_order_for_packer` backed by function
`enforce_single_active_order_for_packer`, plus related team-change triggers that
sync `profiles.current_order_id` and packer status.

## OQ-021 {#oq-021}

### Which attendance capability function is authoritative?

**Impact: Medium. Status: open.**

**What was observed.** `Mobile` calls **both** `can_record_attendance` and
`can_user_mark_attendance`. Only the second has a body in any repository (from the
one migration). The first is declared in the types snapshot with unknown logic.

**Why it matters.** Two capability gates on one action can disagree. Removing
either call without knowing the difference could silently widen or block access.

**What would resolve it.** Dump both function definitions and compare.

## OQ-023 {#oq-023}

### What keeps `packer_sessions` denormalised fields fresh?

**Impact: Low. Status: open.**

**What was observed.** `packer_sessions` stores `order_name`, `client_name` and
`project_lead_name` alongside `order_id`. These are snapshots taken at session
creation. Nothing in source refreshes them.

**Why it matters.** If an order is renamed or a project lead changes mid-session,
the session's copies are stale, and any UI reading them shows outdated values.

**What would resolve it.** Check for triggers on `orders`, `profiles` and
`packer_sessions`.

## OQ-024 {#oq-024}

### Which report packed-date logic is live today?

**Impact: High. Status: closed 2026-08-20.**

**What was observed.** An incident log records the report date logic being changed
to `COALESCE(order_pkg_instance.packed_at, MAX(pkd_item.created_at))` via a
migration named `prefer_instance_packed_at_in_reports`, and then **reverted on
2026-08-08** to `MAX(pkd_item.created_at)`. A further migration named
`add_packing_start_completion_date_modes` exists as an uncommitted file in an older
checkout, implying more work followed.

**Resolved from live Supabase.** The current overload with `p_tag_ids` uses
`COALESCE(order_pkg_instance.packed_at, MAX(pkd_item.created_at))` for
completion-style modes. It accepts `packing_started_at`,
`packing_completed_at`, `item_packed_at`, and falls back to instance creation for
unrecognised modes. `item_packed_at` is a legacy alias for completion.

## OQ-007 {#oq-007}

### `order_teams` or `order_team_members`? — **CLOSED 2026-08-19**

**Resolved from source, from two independent artifacts.**
`order_team_members` exists, with columns `(id, order_id, packer_id, is_team_lead,
created_at)`, declared in `website/src/types/supabase.ts` and created/altered in
`Mobile/supabase/migrations/20250121_add_team_lead_support.sql`. It carries a
unique constraint on `(order_id, packer_id)`, implied by an `ON CONFLICT` clause,
and a partial index on `(order_id, packer_id) WHERE is_team_lead = TRUE`.

**`order_teams` does not exist** in any source. The `Mobile` README is wrong.

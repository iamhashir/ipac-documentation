## Context

IPAC's repositories have been renamed and moved at least once, and the old names
remain visible in git history, in prose inside the applications, and in build
identifiers. Before this was established, source references in this documentation
could not be trusted to resolve.

## Problem

Three different owners appeared in the available evidence, and old GitHub URLs
**redirect** rather than 404 — so a stale remote keeps working and gives no signal
that it is stale. Without a decision, every source link on this site was a guess.

## Decision

**The canonical organisation is `ipacapps`.** Confirmed 2026-08-19.

The canonical repositories:

```text
ipacapps/
├── ipac-documentation
├── website          (formerly it-ipac/admin-panel)
└── Mobile
```

Applied in this repository: `organizationName` and all three repository URLs in
`docusaurus.config.ts` now use `ipacapps`, and `SourceRef` resolves both application
repositories to live links.

## Alternatives

**Not recorded.**

No artifact evaluates keeping the repositories under `it-ipac`, or consolidating them
differently. The rename from `admin-panel` to `website` and the organisation change
are visible only as outcomes.

## Consequences

### Positive

- **Source references resolve.** Every `SourceRef` on this site links to real code.
  Before this decision, `Mobile` paths rendered as plain text because inventing a URL
  was not acceptable.
- **One place to change.** Repository URLs live in `customFields.repositories` in
  `docusaurus.config.ts`. If the organisation changes again, one edit updates every
  link on the site.
- **`Mobile` is in an organisation, not a personal account.** An earlier checkout of
  the same application had `origin` and `upstream` pointing at two *personal*
  accounts. That was the single largest bus-factor risk identified in the audit, and
  the current remote resolves it.
- **Two open questions closed** — OQ-001 and OQ-010.

### Negative

- **Old names persist in three places**, and they will keep confusing readers:

  | Location | Still says |
  | --- | --- |
  | `website/docs/ARCHITECTURE.md`, `DEVELOPMENT.md`, `ROLES.md` | `admin-panel/` and `ipac_mobile/` |
  | `Mobile/README.md` | a personal-account clone URL and `cd ipac-operations-app` |
  | `website/package.json` | `"name": "ipac-admin-panel"` |
  | `Mobile/app.json` | `slug` and `scheme` of `ipac-operations-app`; Android package `com.ipacoperationsapp.app` |

- **`ipac_mobile` never existed as a directory.** It appears in `website`'s own
  documents, including a workspace-layout diagram, and would fail a new developer's
  first `cd`.
- **The reason is lost.** Nobody reading this will know whether the move was
  organisational, administrative, or incidental.

### Risks

- **Silent link rot.** Because GitHub redirects old URLs, a wrong organisation name
  produces links that *work* — so the error is invisible until the redirect stops.
  This is why the organisation is stated as a decision here rather than inferred.
- **`ipac-documentation` is unverified.** It is configured as
  `ipacapps/ipac-documentation` for consistency, but the repository does not exist
  yet, so no remote confirms it.

:::danger Load-bearing identifiers must not be renamed automatically

`Mobile/app.json` still declares names derived from `ipac-operations-app`. **Do not
"finish" the rename by changing them.** They are not cosmetic:

| Identifier | Value | Why renaming is a product decision |
| --- | --- | --- |
| `android.package` | `com.ipacoperationsapp.app` | This **is** the installed application's identity. Change it and you ship a *different app*: existing installs will not upgrade, and any store listing identity is lost. |
| `scheme` | `ipac-operations-app` | Backs deep links. Changing it breaks every link already issued. |
| `slug` | `ipac-operations-app` | Ties the project to its EAS identity, and EAS owns version numbering (`appVersionSource: "remote"`). |

The distinction that matters: **prose names are simply wrong and should be corrected;
build identifiers are correct as they stand and carry migration consequences.** This
documentation corrected the prose on its own pages and did not touch either
application. Tracked as [OQ-003](/docs/reference/open-questions#oq-003).

:::

## Current State

**In effect.** Both application checkouts have exactly one remote each, under
`ipacapps`. No `it-ipac` remote is configured in either.

Remaining work is in the application repositories, not here: correcting the stale
prose names, and separately deciding whether the `app.json` identifiers should ever
change.

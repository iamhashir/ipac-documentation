# Roles and permissions

**IPAC does not have one role model. It has four, and they disagree.**

This page documents that divergence exactly as source and live database state
show it. It does not reconcile the four into a single table, because doing so is
a product and authorization-design decision.

## Role names referenced anywhere in source

`admin` · `director` · `executive` · `sales` · `client` · `packer`

Live `roles.name` rows are `admin`, `client`, `executive`, `packer`, and
`sales`. There is no live `director` row today, even though source checks for it.

`team_lead` is **not a role**. It is `order_team_members.is_team_lead`, a boolean
scoped to one order. A packer can be team lead on one order and not on another.
Treating it as a global role is a category error that the codebase itself warns
about.

## The four enforcement points

### 1. `website` page access

<SourceRef repo="website" path="src/lib/access.ts" symbol="FULL_ACCESS_ROLES" />

| Role | Access |
| --- | --- |
| `admin`, `director`, `executive`, `sales` | All 10 admin pages |
| `client` | `/dashboard`, `/my-orders`, `/reports` only |
| `packer` | None — bounced to login |
| anything else | None |

The file's own comment describes `executive` as "the CEO tier (treated as full
access)". Enforcement is a client-side `useEffect` redirect via
`useRequirePageAccess`, and one page — `/inventory` — omits it entirely
([H1](/docs/security/findings#h1)).

### 2. `Mobile` route guards

<SourceRef repo="Mobile" path="app/index.tsx" /> and the two group layouts.

| Role | Destination |
| --- | --- |
| `admin`, `director`, `sales` | `(admin)` group |
| `packer` | `(packer)` group |
| anything else | redirected to `/auth/login` |

### 3. `create-user` Edge Function

<SourceRef repo="Mobile" path="supabase/functions/create-user/index.ts" />

Permits `director` or `admin` only. Anything else receives 403.

### 4. Database function `can_user_mark_attendance`

<SourceRef repo="Mobile" path="supabase/migrations/20250121_add_team_lead_support.sql" />

Grants when the role is `admin` or `director` **and** `profiles.status = 'active'`,
**or** when the caller is team lead for that order. `SECURITY DEFINER`, granted to
`authenticated` — so this one cannot be bypassed by a client.

## The divergence, side by side

| Role | `website` pages | `Mobile` app | Can create users | Can manage attendance |
| --- | --- | --- | --- | --- |
| `admin` | Full | admin group | **Yes** | **Yes** |
| `director` | Full | admin group | **Yes** | **Yes** |
| `executive` | **Full** | **Locked out** | No | No |
| `sales` | **Full** | admin group | No | No |
| `client` | 3 pages | **Locked out** | No | No |
| `packer` | None | packer group | No | Only as team lead |

Two consequences are verified from source, not speculation:

:::danger `executive` cannot use Mobile at all

`executive` receives full access to every page of `website`, and is not handled
by any Mobile branch. Mobile's entry route sends unrecognised roles to
`/auth/login`, and the admin layout renders "Access denied. Redirecting…". An
executive user therefore cannot open the field application.

This matters because `executive` is one of the role names that internal documents
list as **live**, while `director` — which both Mobile and the Edge Function
depend on — is **not** on that list.

:::

:::warning `director` does not exist live

Live verification confirmed no `director` role row. User creation via the Edge
Function therefore works for `admin` only, and attendance management reduces to
`admin` plus per-order team leads. Nothing in source fails loudly — the checks
simply never match.

:::

## Permission flags are database-side only

The `roles` table carries six booleans:

```text
can_manage_roles      can_ban_users        can_block_users
can_delete_profiles   can_reset_passwords  can_unblock_users
```

A `user_effective_permissions` view exists, as do `user_has_permission` and
`get_user_role` functions.

**No authorization decision in either application, or in the Edge Function, reads
any of them.** Every check compares role names. The Edge Function even selects
`can_manage_roles` alongside the role name and then ignores it.

Live RLS does enforce some flags through `user_has_permission`, so the flags are
not inert. They still do **not** correspond to the page-level access model.
There are no page-access flags in the database, so page access is purely a
frontend concern.

## Temporary privileges

`temporary_privileges` holds `user_id`, `granted_role_id`, `granted_by`,
`expires_at`, `is_active` and `reason`. A `deactivate_expired_privileges`
function exists and **no application calls it**, which implies a trigger or
scheduled job.

Time-boxed role elevation is therefore part of the database authorization design.
Live verification found zero temporary privilege rows on 2026-08-20.

## Rules for working with roles

Until the role model is unified:

1. **Do not infer access from a role name.** Check all four enforcement points.
2. **Do not add a role** without deciding its behaviour in all four.
3. **Do not rename or remove a role.** Four hardcoded lists depend on the strings,
   and nothing will fail at compile time.
4. **Do not use permission flags for page access** until the frontend model is designed.
5. **Do not treat `team_lead` as a role.** It is per-order state.

## What would resolve this

The live role set is now known. What remains is a design decision: one shared
definition of role capability, with the other layers derived from it rather than
restating it.
